Great engineering problem — and you're right that access is the first hurdle. Here are the realistic approaches, roughly in order of power vs. complexity:

Option 1: SQLite Direct Read (Most Powerful)

iMessage stores everything in a local SQLite database:

~/Library/Messages/chat.db

This is the richest approach for categorization — full message history, timestamps, sender info, attachments, thread structure. You'd need to grant your agent Full Disk Access in System Settings → Privacy & Security. From there it's just SQL:

sql

SELECT message.text, handle.id, message.date

FROM message

JOIN handle ON message.handle_id = handle.rowid

ORDER BY message.date DESC;

The date column is in Apple's epoch format (nanoseconds since Jan 1, 2001) so you'd convert it. This is the right foundation for a categorization pipeline — feed chunks to an LLM, get structured labels back.

Option 2: AppleScript

Good for sending and basic reading without Full Disk Access:

applescript

tell application "Messages"

    set theChats to every chat

    repeat with aChat in theChats

        log name of aChat

    end repeat

end tell

More limited than the SQLite approach — you can't easily bulk-export message text — but it's sandboxed and doesn't require elevated permissions.

Option 3: Accessibility API (UI Automation)

This is essentially what Cowork does under the hood — use macOS Accessibility to drive the Messages UI programmatically. Python via pyautogui or the native ApplicationServices framework. Works but is fragile (UI changes break it) and slow for bulk processing.

Option 4: Shortcuts + Automation

Apple Shortcuts has a "Get Messages" action. You could trigger a Shortcut from Python via subprocess calling shortcuts run. Limited but sandboxed and Apple-blessed.

Recommended Stack for Your Use Case

Given your background, I'd go:

  1. Python agent reads chat.db via sqlite3 (stdlib, no deps)
  2. Chunked LangChain pipeline — you already have the LCEL patterns from sushi-rag
  3. Claude API call to classify/categorize each thread
  4. Output to JSON or a simple local vector store (ChromaDB) for querying

The main gotcha is that chat.db requires Full Disk Access, and on macOS Sequoia (which you're on) you'll need to explicitly grant that to Terminal or your Python runtime in System Settings.

Recognized straightforward technical database query

Recognized straightforward technical database query

Python's built-in sqlite3 module is the simplest and best option — no dependencies, no install, already on your Mac.

python

import sqlite3

import os

from datetime import datetime, timedelta

 

# Apple's epoch starts Jan 1, 2001 — convert to Unix timestamp

APPLE_EPOCH_OFFSET = 978307200

 

def apple_ts_to_datetime(ts):

    if ts is None:

        return None

    # Stored in nanoseconds in newer macOS versions

    ts_seconds = ts / 1e9

    return datetime.utcfromtimestamp(ts_seconds + APPLE_EPOCH_OFFSET)

 

db_path = os.path.expanduser("~/Library/Messages/chat.db")

conn = sqlite3.connect(db_path)

conn.row_factory = sqlite3.Row  # access columns by name, not index

cursor = conn.cursor()

 

cursor.execute("""

    SELECT

        message.rowid,

        message.text,

        message.is_from_me,

        message.date,

        handle.id AS sender

    FROM message

    LEFT JOIN handle ON message.handle_id = handle.rowid

    WHERE message.text IS NOT NULL

    ORDER BY message.date DESC

    LIMIT 100

""")

 

for row in cursor.fetchall():

    print({

        "sender": row["sender"],

        "text": row["text"],

        "is_from_me": bool(row["is_from_me"]),

        "date": apple_ts_to_datetime(row["date"])

    })

 

conn.close()

Key Things to Know About chat.db

Main tables you'll use:

Table

What's in it

message

Every message — text, date, is_from_me, flags

handle

Phone numbers / Apple IDs of contacts

chat

Conversation threads

chat_message_join

Links messages to threads

chat_handle_join

Links handles to threads

To get full threads (not just messages):

python

cursor.execute("""

    SELECT

        chat.chat_identifier,

        message.text,

        message.is_from_me,

        message.date,

        handle.id AS sender

    FROM message

    JOIN chat_message_join ON message.rowid = chat_message_join.message_id

    JOIN chat ON chat_message_join.chat_id = chat.rowid

    LEFT JOIN handle ON message.handle_id = handle.rowid

    WHERE message.text IS NOT NULL

    ORDER BY chat.rowid, message.date ASC

""")

Gotchas

  • Full Disk Access — grant it to Terminal (or VS Code / your IDE) in System Settings → Privacy & Security → Full Disk Access. Without it you'll get a permissions error.
  • Open the DB read-only to avoid any risk of corruption: sqlite3.connect(f"file:{db_path}?mode=ro", uri=True)
  • Reactions and tapbacks are stored as messages with associated_message_type != 0 — filter those out with WHERE message.associated_message_type = 0
  • Attachments are a separate table (attachment) joined via message_attachment_join

One Honest Caveat on Blocking

True programmatic blocking (the equivalent of tapping "Block Contact" in Messages) requires either Accessibility API access or a native Swift bridge — AppleScript alone can't reliably trigger it. The agent handles this pragmatically: it writes blocked senders to blocked_senders.txt and skips them on every future run. For full blocking, open the thread in Messages before it gets deleted and hit Details → Block Contact. That's a one-time manual step per spammer.
